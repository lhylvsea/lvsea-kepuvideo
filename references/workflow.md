# 科普视频工作流合同

本文件把 X 原文中的十步流程抽象成可复用合同。主题、时长和受众是变量；相对论、60 秒和原文示例不进入默认规则。

## 0. 建立任务契约

在项目根写 brief.md，至少包含：

| 字段 | 说明 |
|---|---|
| source | 主题、URL、文件、文章或脚本 |
| audience | 观众已知什么、真正卡在哪里 |
| core_question | 这一条视频只回答的一个问题 |
| target_duration_sec | 用户目标时长，最终以实测配音和渲染文件为准 |
| ratio | 默认 9:16；用户指定优先 |
| voice_and_captions | 声音、语速、试听、外置/烧录字幕 |
| visual_direction | 信息动画、抽象图解、颜色、禁用项 |
| rights | 原文、图片、字体、声音、音乐和上传授权 |
| confirmed / inferred / unknown | 事实、推测和待核实项 |

目标时长只用于初始规划。中文口播字数可先按约 230–300 字/分钟作为工程估算，不把它当成质量或语速真值；生成音频后以 ffprobe 和 voice.srt 的实际时长重建后续时间轴。

## 1. 事实底稿和研究

### 有文章或脚本

- 保存原文索引，不覆盖用户源文件；
- 把主张分为来源直接证明、自述/二手转述、作者推断和未知；
- 记录数字、日期、单位、专名、公式、限制条件和来源；
- 需要公开事实时查一手来源，无法核验的主张降级或保留待核实项；
- 只有确认事实边界后才进入口播改写。

### 只有主题

- 先把主题缩成一个可解释的问题；
- 对时间敏感、行业、政策、健康、安全、金融和产品能力做实时核验；
- 生成 article.md 时把来源或证据写在工程文件中，不把检索脚手架塞进旁白；
- 先显示底稿、范围和待核实项，等用户确认或按已授权的默认继续。

长视频可以分章，但章节共享一个主问题。例如“膨润土是什么、为什么能吸水、在几个工业场景里怎么发挥作用、有哪些边界”可以是一条主问题的递进；不要把互不相关的主题拼成五分钟。

## 2. 从文章到口播

保存 script.md，并按以下合同改写：

- 开头尽快让观众知道要解决什么问题，不先写“本文将”；
- 句子按朗读节奏组织，主语和动作尽量提前；
- 一个镜头/一段口播只推进一个事实、机制、例子或限制；
- 必须保留数字、名称、单位、条件、归属和不确定性；
- 专业术语第一次出现时给能听懂的解释，不能为了顺口改变技术含义；
- 目标时长通过内容取舍和自然停顿控制，不能靠极端加速；
- 先做普通口播稿，再进入最后的 lvsea-writing 编辑层。

口播稿完成后执行一次朗读检查：记录卡顿句、同音歧义、数字读法、英文缩写、过密术语和需要停顿的位置。不要用固定的“嗯”“其实吧”、错别字或虚构个人经历制造人味。

## 3. lvsea-writing 最后编辑门

具体适配见 writing-adapter.md。顺序必须是：

~~~text
事实/证据 -> 主线和篇幅 -> 初稿口播 -> lvsea-writing 改稿/去模板 -> 朗读复查 -> 作者/用户确认
~~~

不要在文章尚未确定时先做“去 AI 味”。如果最后编辑改变了数字、名称、结论或技术含义，回到证据账本并重做相关检查。

## 4. 试听和完整配音

默认使用 edge-tts 或用户指定的已授权声音：

1. 检查命令和可用普通话声音；
2. 用同一速度从 script.md 前 80–120 字生成 sample-1/2/3；
3. 报告每个样本的 voice 名称、参数、文件路径；
4. 停止，等待用户选定；不得未经选择生成完整音频；
5. 生成 voice.mp3 和 voice.srt；
6. 用 ffprobe 读取音频编码、采样率、声道和实际时长；
7. 校验 SRT 时间不倒退、无重叠、覆盖整段音频；若发现问题先修时间轴，不继续画面。

如果用户提供现成音频，记录文件来源和授权，仍然用实际音频时长和转录/字幕时间轴作为时钟。

## 5. 分镜合同

storyboard.md 每个镜头必须有：

~~~text
scene_id
start
end
voice_text
narrative_role
visual_goal
screen_text
animation
assets
source_or_fact_refs
subtitle_safe_area
exit_condition
~~~

设计原则：

- 画面解释正在说的内容，不把完整口播全文贴在画面上；
- 优先 SVG、HTML、卡片、数字、曲线、流程、时间线、对比和简单图标；
- 一个镜头只承担一个主要信息；
- 不为了“丰富”每两秒切一次，不用装饰动画填空；
- 字幕按真实 SRT 时间轴显示，放在平台安全区，按语义手动断行；
- 长句两行的视觉宽度尽量接近 1.2:1，达到约 1.35:1 时重新断行或压缩措辞；
- 记录来源图片和授权；没有可用事实图片时使用抽象图解，不抓取来源不明图片。

完成 storyboard.md 后停止，让用户检查镜头职责、文字、事实和画面方向。没有确认就不要开始正式 HyperFrames 制作。

## 6. HyperFrames 预览循环

读取 hyperframes 入口，并按需读取 core、animation、creative、media、CLI 规则。以音频和 SRT 为主时钟，制作 9:16、1080×1920、30fps 的 HTML/CSS/SVG 组合。

最低循环：

~~~text
author -> lint -> validate -> inspect -> preview -> user review -> patch -> repeat
~~~

局部修改请求必须带时间范围、问题和目标。补丁合同默认包含：

~~~text
只修改 [start] 到 [end]。
不要修改配音、字幕内容、字幕时间轴、其他镜头和总时长。
把画面从 [现状] 改成 [目标视觉]。
完成后重新运行 lint/validate/inspect，保持原预览服务或说明新的预览地址。
~~~

不要把预览通过写成最终质量证明。预览之后仍要完整观看并做最终媒体验收。

## 7. 最终渲染与验收

渲染前确认：

- 目标时长和 voice.mp3 一致；
- voice.srt 完整覆盖音频；
- 每个主要镜头有首帧、转折和尾帧检查；
- 没有 runtime、motion、lint、布局、字体或素材加载错误；
- 没有黑帧、异常空镜、异常静音或音频尾部截断；
- 字幕、画面内文字和 SVG 不越界、不被裁切、不侵入安全区；
- 使用的图片、字体、音乐、声音和人物素材都有来源/授权记录。

最终输出建议为 1080×1920、30fps、H.264 视频、AAC 音频，除非用户指定其他规格。用 ffprobe 读取实际分辨率、帧率、编码、音频编码、总时长和文件大小；视觉抽帧与人工审看结果写入 reports/final-check.md。

## 8. 停止和恢复

- 任何阶段失败都保留已完成产物，不删除项目；
- 工具超时后先检查进程、文件和日志，再判断失败；
- 同一修复连续失败两次时，重新读取完整错误并建立最小复现，不重复猜测；
- 已确认阶段只做确定性检查或局部修复时可连续推进；
- 主题、受众、主判断、版权、费用或输出格式改变时使用 grilling 重新收敛。
